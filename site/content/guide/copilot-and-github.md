## 二つは別のもの

Copilotアプリで頼んだのに、GitHubのページを開いても何も変わっていない。仲間が「直した」と言うのに、自分の画面には出てこない。こうした戸惑いは、「Copilotアプリ」と「GitHub」を同じものだと思っていると起こりがちです。二つは別のものです。

- Copilotアプリ：AIに頼みごとをして、会話をするための「窓口」。自分のパソコンにインストールしたアプリです（[Copilotデスクトップアプリを使い始める](copilot-app.md)）。
- GitHub：ファイルとその変更の記録（履歴）を保管する、インターネット上の「保管庫」。ブラウザで`github.com`を開くと見られます（[GitHubとは](github-basics.md)）。

たとえるなら、GitHubはチーム共有の書庫、自分のパソコンは自分の机、Copilotアプリは机で一緒に働く助手に話しかけるための窓口です。助手（Copilotのエージェント）は、書庫から借りてきたコピーを机の上で書き換えます。書き換えたものは、書庫に返す（GitHubに送る）までは、ほかの人には見えません。

## 三つの場所

実際には、場所が三つあると考えると分かりやすくなります。

<figure class="fig">
{{svg:copilot-github-places.svg}}
<figcaption>Copilotアプリは頼む窓口、自分のパソコンはファイルが実際に変わる作業場所、GitHubはチームで共有する保管庫。パソコンとGitHubの間は、プッシュ（送る）とプル（取ってくる）でつながる。</figcaption>
</figure>

| 場所 | 何があるか | だれのものか |
| :---- | :---- | :---- |
| Copilotアプリ | あなたとAIの会話（チャット、セッション） | 自分だけ |
| 自分のパソコン | リポジトリのコピー（ファイルと履歴） | 自分だけ |
| GitHub | リポジトリの正式な置き場所（ファイルと履歴） | チーム全員 |

アプリにリポジトリを「プロジェクト」として加えると、GitHubのリポジトリが自分のパソコンに複製されます。これをクローン（clone）と言います。エージェントが書き換えるのは、このパソコンの中のコピーです。GitHubのファイルを、アプリが直接書き換えているわけではありません。

<div class="box note" markdown="1">
<p class="box-title">チャットはファイルの保管場所ではない</p>

チャットに書いた文章や、AIが返した文章は、リポジトリのファイルではありません。チャットを削除してもファイルは消えませんし、逆に、チャットで「いい案ですね」と言い合っただけでは、ファイルには何も残りません。残したいこと（チームで決めたこと、企画の方針など）は、READMEなどのファイルに書いてもらい、コミットしてGitHubに送ります。新しいセッションのエージェントは、前のセッションの会話を覚えていませんが、リポジトリのファイルは読めます（[指示ファイル](copilot-agent.md)）。

</div>

## 一つの変更がGitHubに届くまで

Copilotアプリで頼んだ変更は、次の六つの段階を通って、チームの正式な版（`main`）に入ります。

<figure class="fig">
{{svg:copilot-github-journey.svg}}
<figcaption>頼んだ変更がmainに入るまで。赤い点線より左は自分のパソコンの中だけの出来事で、仲間やGitHubのページからは見えない。</figcaption>
</figure>

<ol class="steps">
<li>頼む：Copilotアプリのチャットに、してほしいことを書きます。この時点では、まだ何も変わっていません。</li>
<li>書き換え：エージェントが、パソコンの中のファイルを書き換えます。アプリの<span class="ui">Changes</span>で、何が変わったか（差分）を確かめます。</li>
<li>コミット：変更を、説明（コミットメッセージ）をつけて履歴に記録します。記録はまだ自分のパソコンの中だけです。</li>
<li>プッシュ：コミットを、GitHubに送ります。ここで初めて、GitHubのページに変更が現れます。ただし、作業用のブランチの上です。</li>
<li>プルリクエスト：「このブランチの変更を<code>main</code>に取り込んでください」という提案を、GitHubの上に作ります。仲間は、ここで変更を読んで意見を言えます。</li>
<li>マージ：確かめたら、変更を<code>main</code>に合流させます。仲間は、自分のパソコンにプル（取り込み）すると、その変更を受け取れます。</li>
</ol>

公式のドキュメントによれば、Copilotアプリでは、2と3の作業はセッション専用のブランチの上で進み、<span class="ui">Create PR</span>を押すと5のプルリクエストが作られます（[Copilotデスクトップアプリを使い始める](copilot-app.md)）。コミットやプッシュをアプリがどこまで自動で行うかは、このサイトではまだ画面で確かめていません（2026年11月4日時点）。分からなくなったら、アプリのチャットで次のように聞くのが確実です。

- 「いまの変更は、コミットされていますか。GitHubにプッシュされていますか」
- 「いま作業しているのは、どのブランチですか」
- 「変更をコミットして、GitHubにプッシュしてください」

## それぞれの言葉の意味

### リポジトリ

プロジェクトのファイルと、その変更の履歴をまとめた箱です。GitHubの上にある正式なものと、各自のパソコンにあるコピーがあります。どちらも同じリポジトリですが、プッシュとプルをしない限り、中身は自動ではそろいません。

### ブランチ

`main`から枝分かれした、作業用の流れです。`main`はチームの「いまの正式な版」で、発表やサイトの公開にはふつう`main`を使います。ブランチの上でいくら書き換えても、`main`には影響しません。Copilotアプリでは、セッションごとに専用のブランチが作られるので、エージェントの作業が途中で`main`に混ざることはありません。

ブランチがあるので、自分のセッションと仲間のセッションを同時に進めても、ぶつかりにくくなります。ボタンを押して、ブランチの動きを試してみましょう。

<div class="demo" data-demo="branch-sim"></div>

詳しくは[ブランチとプルリクエストでの共同作業](github-collaboration.md)にあります。

### コミット

ファイルの変更を、説明をつけて履歴に記録することです。また、その記録の一つ一つのことも言います。ファイルを保存しただけでは、コミットにはなりません。コミットしておけば、あとで「いつ、何を、なぜ変えたか」を確かめたり、前の状態に戻したりできます。エージェントに頼むと、コミットメッセージもエージェントが書きます（[コミットを読む・書く](commit-messages.md)）。

### プッシュ

自分のパソコンにあるコミットを、GitHubに送ることです。コミットしてもプッシュしなければ、GitHubにも仲間にも届きません。パソコンが壊れたら、プッシュしていない変更は失われます。

### プル

GitHubにある新しいコミットを、自分のパソコンに取ってくることです。仲間がGitHubに入れた変更は、プルするまで自分のパソコンには届きません。「仲間の変更が見えない」ときは、たいていこれが原因です。

### プルリクエスト

ブランチの変更を`main`に取り込んでほしいという提案です。略してPRと言います。GitHubの上に、変更の中身、説明、話し合いをまとめたページができます。名前に「プル」が入っていますが、上の「プル」（取ってくる）とは別の操作です。

### マージ

ブランチの変更を`main`に合流させることです。プルリクエストのページの<span class="ui">Merge pull request</span>などのボタンで行います。マージして初めて、変更がチームの正式な版になります。マージの方法の違いは[ブランチとプルリクエストでの共同作業](github-collaboration.md)にあります。

## どこで何を確かめるか

| 知りたいこと | 見る場所 |
| :---- | :---- |
| AIが何を書き換えたか | Copilotアプリの<span class="ui">Changes</span> |
| AIと何を話したか | Copilotアプリのチャット（セッション） |
| チームの正式な版のファイル | GitHubのリポジトリのページ（ブランチが`main`になっているか確かめる） |
| 作業用のブランチの中身 | GitHubのリポジトリのページで、左上の<span class="ui">main ▾</span>からブランチを切り替える |
| 取り込みを待っている変更 | GitHubの<span class="ui">Pull requests</span>のタブ |
| これまでの変更の記録 | GitHubの<span class="ui">Commits</span>（ファイル一覧の上の時計のアイコン） |

英語の画面の言葉は[英語の画面を読むための単語帳](github-english-ui.md)で調べられます。

## よくある勘違い

| こんなとき | よくある原因と、すること |
| :---- | :---- |
| Copilotで直したのに、GitHubのページに出てこない | まだコミット、プッシュをしていないか、GitHubで`main`を見ているのに変更は作業用のブランチにある。アプリで「プッシュされていますか」と聞き、GitHubではブランチを切り替えるか、プルリクエストを見る。 |
| プルリクエストを作ったのに、`main`が変わらない | プルリクエストは提案で、まだマージされていない。内容を確かめてマージする。 |
| 仲間がマージした変更が、自分のアプリやパソコンに出てこない | まだプルしていない。新しいセッションを始める前に、アプリに「GitHubの最新の`main`を取り込んでください」と頼む。 |
| パソコンのフォルダーを開いても、変更が見当たらない | セッションを<span class="ui">New worktree</span>で始めると、変更は別の作業用フォルダーに入る（[ワークツリー](git-worktree.md)）。アプリの<span class="ui">Changes</span>で確かめる。 |
| チャットを消したら、作ったファイルも消える？ | 消えない。チャットとファイルは別のもの。逆に、チャットに書いただけのことはファイルに残らない。 |
| GitHubのウェブ画面で直接ファイルを直してもよいか | よい。ただし、その変更はGitHubの上にだけある。自分や仲間のパソコンには、プルするまで届かない。 |
| 二人が同じファイルを直したら、ぶつかった | 衝突（コンフリクト）と言う。[衝突の直し方](github-collaboration.md)を見るか、アプリのエージェントに直し方を相談する。 |

## チームでプロジェクトを進めるときの約束

グループのプロジェクトでは、一つのGitHubのリポジトリを全員で使い、各自が自分のパソコンのCopilotアプリで作業します。次のことを決めておくと、混乱が減ります（資料外の助言を含む）。

- リポジトリは一つにして、全員を共同作業者に招待する。各自が別々にリポジトリを作ると、変更が合わさらない。
- 作業を始める前に、GitHubの最新の`main`をプルする。
- 一つのセッションでは、一つのまとまった作業を頼む（例：「旅行プランの入力画面を作る」）。
- 作業が終わったら、早めにプルリクエストを作り、仲間に知らせる。長く寝かせたブランチほど、衝突が起きやすい。
- だれかのプルリクエストを、別のだれかが読んでからマージする。少なくとも自分で<span class="ui">Files changed</span>を読む。
- 決めたことはチャットではなく、リポジトリのファイル（READMEなど）に書いて残す。
- パスワード、APIキー、個人情報は、リポジトリにもチャットにも書かない（[AIを使うときの倫理とルール](ai-ethics.md)）。

チームの役割分担や連絡の取り方は[チームでプロジェクトを進める](teamwork.md)にあります。

<div class="box try" markdown="1">
<p class="box-title">やってみよう</p>

グループのリポジトリで、だれか一人がCopilotアプリのセッションを始め、「READMEに、グループのメンバーの役割を書く欄を作ってください」と頼みます。<span class="ui">Changes</span>で変更を確かめ、プルリクエストを作ってマージします。そのあと、ほかのメンバーがGitHubのページで`main`のREADMEが変わったことを確かめ、自分のアプリで最新の`main`をプルしてから、自分の役割を書き足すよう頼んでみましょう。一つの変更が、アプリからGitHubを通って仲間に届くまでの流れが体験できます。

</div>
