## 知識ベースとは

プロジェクトを進めると、集めた資料、調べたこと、決めたこと、AIとのやり取りで分かったことがどんどん増えていきます。これらがチャットの履歴やパソコンのあちこちに散らばると、あとで「あの情報はどこだっけ」と探すことになります。知識ベースは、そうした情報を一か所に集め、整理し、いつでも引けるようにしたものです。

第2回（2026年10月7日）の授業では、GitHubとAndrej Karpathyが提案した「LLM Wiki」の考え方を使い、AIエージェントで知識ベースを作る方法が実演されました（[第2回の記録](../../../wiki/course/sessions/session-02.md)）。この授業の知識ベース（このサイトの「Wiki」）も、その方法で作られています。このページでは、同じ方法を自分のプロジェクトで使う手順を説明します。

## LLM Wikiの考え方

AIに資料を読ませて質問する方法としては、資料をアップロードしておき、質問のたびにAIが関連する部分を探して答える、というやり方がよく使われます。便利ですが、AIは質問のたびに知識を一から組み立て直すので、何も蓄積されません。

LLM Wikiでは、AIエージェントが資料を読むたびに要点を抜き出し、互いにリンクしたMarkdownのページ（Wiki）に書き込みます。新しい資料が来れば、関係するページを書き足し、古い記述との食い違いを記録します。資料を足すたびに、質問をするたびに、Wikiが育っていきます（[LLM Wiki](../../../wiki/concepts/llm-wiki.md)）。

人間の役割は、資料を選び、探究の方向を決め、よい問いを立てることです。要約、相互参照、整理、記録といった地道な作業はエージェントが引き受けます。考え方の全体は[LLM Wiki（日本語版）](../../../llm-wiki-j.md)にまとめられています。少し長い文書ですが、自分で作る前に一度読んでおくと理解が深まります。

## 三つの層

LLM Wikiの知識ベースは、三つの層でできています。

<figure class="fig">
{{svg:knowledge-base-layers.svg}}
<figcaption>元資料、Wiki、スキーマの三つの層。人間は資料を置いてWikiを読み、エージェントはスキーマに従ってWikiを書く。</figcaption>
</figure>

- 元資料（`raw/`）：自分で集めた資料を置くフォルダー。記事、論文、メモ、画像など。エージェントは読むだけで、書き換えない。事実の拠り所になる。
- Wiki（`wiki/`）：エージェントが書くページのフォルダー。資料ごとの要約、人物や用語のページ、テーマのまとめ、目録（`index.md`）、作業記録（`log.md`）などが入る。
- スキーマ（`AGENTS.md`）：Wikiの構成、書き方、作業の手順をエージェントに伝える文書。エージェントを「なんでも答えるチャットボット」から「規律あるWikiの管理人」に変えるのは、この文書。

## 三つの操作

知識ベースでの作業は、主に三つの操作に分かれます。英語ではそれぞれingest、query、lintと呼ばれます。どれも、エージェントに日本語で頼めば進められます。

| 操作 | 頼み方の例 | エージェントがすること |
| :---- | :---- | :---- |
| 取り込み | 「raw/に置いた資料を取り込んでください」 | 資料を読み、要約ページを作り、関係するページを更新し、目録と作業記録に反映する。 |
| 質問 | 「これまでの資料から、〇〇について分かっていることをまとめてください」 | 目録から関係するページを探して読み、出典つきで答える。役立つ答えはページとして保存する。 |
| 点検 | 「Wikiを点検してください」 | ページ間の矛盾、古い記述、リンク切れ、どこからもリンクされていないページなどを探して直す。 |

## 作り方

ここでは、GitHubの画面とAIエージェントを使って、最小限の知識ベースを作る手順を説明します。GitHubの基本操作は[GitHubを始める](github-first-steps.md)を、エージェントの使い方は[Copilotのエージェントに作業を頼む](copilot-agent.md)と[AIエージェントとは](ai-agents.md)を見てください。

<ol class="steps">
<li>GitHubで新しいリポジトリを作る。名前は半角の英小文字とハイフンで（例：<code>my-project-wiki</code>）。最初は非公開（<span class="ui">Private</span>）にしておくのが安全。<span class="ui">Add a README file</span>にチェックを入れると、空のリポジトリにならず作業しやすい。</li>
<li>この授業のリポジトリから<code>llm-wiki-j.md</code>をコピーして、自分のリポジトリの一番上に置く。エージェントが考え方を理解するための参照文書になる。</li>
<li>リポジトリの一番上に<code>AGENTS.md</code>を作る。下のひな形を写して書き換えてもよいし、エージェントに「llm-wiki-j.mdを読んで、このプロジェクト用のAGENTS.mdを作ってください。目的は〇〇です」と頼んで作ってもらってもよい。</li>
<li>使うエージェントが独自の指示ファイルを読む場合は、そのファイルも作り、「AGENTS.mdに従うこと。」とだけ書く（例：Claude Codeなら<code>CLAUDE.md</code>）。</li>
<li><code>raw/</code>フォルダーを作り、最初の資料を置く。GitHubの画面では、<span class="ui">Add file</span>から<span class="ui">Create new file</span>を選び、ファイル名の欄に<code>raw/first-note.md</code>のように書くと、フォルダーごと作れる。</li>
<li>エージェントに「AGENTS.mdに従って、raw/first-note.mdを取り込んでください」と頼む。</li>
<li>エージェントが作った変更（プルリクエストやコミット）を開き、要約が資料と合っているか、変なことが書かれていないかを確かめてから取り込む。</li>
</ol>

<div class="box note" markdown="1">
<p class="box-title">補足</p>

`AGENTS.md`は、多くのAIエージェントが共通して読む指示ファイルの名前です（[AGENTS.md](https://agents.md/)）。GitHub Copilotも、リポジトリにある`AGENTS.md`を指示として読む機能を備えています（[GitHub Docs](https://docs.github.com/ja/copilot/how-tos/configure-custom-instructions/add-repository-instructions)、2026年10月7日確認）。エージェントによっては別の名前のファイルを読むので、上の手順4のように「AGENTS.mdに従うこと」とだけ書いたファイルを置いておけば、複数のエージェントで同じ約束事を共有できます。この授業のリポジトリもそうしています。

</div>

## AGENTS.mdのひな形

`AGENTS.md`は長くなくてかまいません。まずは次のような短いものから始め、運用しながらエージェントと相談して書き足していきます。この授業の知識ベースの[AGENTS.md](../../../AGENTS.md)は、もっと詳しく書かれた実例です。

```
# AGENTS.md：〇〇プロジェクトの知識ベース

このリポジトリは、〇〇について調べるプロジェクトの知識ベースです。
llm-wiki-j.mdの考え方にもとづき、エージェントがwiki/のページを書き、維持します。

## 構成
- raw/：人間が置いた資料。読むだけで、変更しない。
- wiki/index.md：全ページの目録（リンクと一行の要約）。
- wiki/log.md：作業記録。追記のみ。
- wiki/sources/：資料ごとの要約ページ。
- wiki/のそのほかのページ：人物、用語、テーマなどのページ。

## 取り込みの手順
1. 資料を読み、要点を利用者に短く報告する。
2. wiki/sources/に要約ページを作る。
3. 関係するページを作るか更新する。
4. index.mdとlog.mdを更新する。
5. 一件の取り込みを一つのコミットにする。

## 書き方
- 日本語で書く。llm-wiki-j.mdの「日本語で書くための規則」に従う。
- 資料にもとづく事実と、推測を区別する。事実には出典のページへのリンクを付ける。
- 他人の個人情報は書かない。
```

ひな形の中で、「日本語で書くための規則」はとくに大切です。段落の途中で改行しない、太字を使わないなどの規則を守らないと、GitHubの画面で日本語が読みにくくなります（[Markdownの書き方](markdown.md)）。

## 取り込みで何が起きるか

資料を一つ取り込むと、エージェントは次のような順に作業します。一つの資料から、要約ページだけでなく、関係する何枚ものページが更新されることもあります。

<figure class="fig">
{{svg:knowledge-base-ingest.svg}}
<figcaption>取り込みの流れ。資料を置くと、エージェントが要約ページを作り、関係するページと目録・作業記録を更新し、まとめてコミットする。</figcaption>
</figure>

取り込みが終わったら、少なくとも次の点を確かめましょう。

- 要約ページの内容が、元の資料と合っているか。資料にないことが書き加えられていないか。
- 推測で補った部分に「要確認」などの印が付いているか。
- `wiki/index.md`に新しいページが載っているか。
- `wiki/log.md`に今回の作業が記録されているか。

GitHubでは、コミットやプルリクエストを開くと、どのファイルのどの行が変わったかが色分けで表示されます。おかしな変更があれば、エージェントに直すよう頼むか、前の状態に戻します（[GitHubとは](github-basics.md)）。

## 毎日の使い方のコツ

- 資料は一件ずつ取り込む：慣れるまでは一件ごとに結果を確かめる。何を重視してほしいか、エージェントに伝えながら進めるとよい。
- 資料はMarkdownかテキストにする：ウェブ記事は本文をコピーしてMarkdownファイルにすると、エージェントが読みやすい。PDFは、文字を選択できる（テキストを含む）ものかを確かめる。
- 自分のメモも資料になる：授業のメモ、思いついたこと、話し合いの記録も`raw/`に置けば、Wikiに組み込まれる。
- 質問の答えを保存する：エージェントにまとめてもらった比較や分析で役に立ったものは、「この答えをWikiのページとして保存してください」と頼む。チャットの履歴に埋もれさせない。
- ときどき点検を頼む：資料が5件ほど増えたら、点検を頼むとよい。矛盾や古い記述が見つかる。
- 作業記録を見る：`wiki/log.md`を読めば、いつ何をしたかが分かる。プロジェクトの記録や発表の材料にもなる。
- AGENTS.mdを育てる：「毎回こう頼んでいる」という手順があれば、AGENTS.mdに書き足してもらう。

<div class="box try" markdown="1">
<p class="box-title">やってみよう</p>

この授業の知識ベースで、質問の操作を試してみましょう。リポジトリを開いたエージェントに「wiki/index.mdを読んで、この授業で使うツールを一覧にしてください。出典のページも示してください」と頼みます。エージェントが目録からページをたどって答える様子が分かります。

</div>

## チームで使う

チームでプロジェクトに取り組むなら、知識ベースを一つのリポジトリで共有すると、全員が同じ情報を見ながら進められます。

- 仲間を招待する：リポジトリの<span class="ui">Settings</span>の<span class="ui">Collaborators</span>から招待する。招待された人は承諾が必要。
- 作業はブランチで：複数の人が同時にエージェントを動かすと、同じページを書き換えてぶつかることがある。各自のブランチで作業し、プルリクエストで確かめてから取り込む（[ブランチとプルリクエストでの共同作業](github-collaboration.md)）。
- 取り込みの担当を決める：だれがどの資料を取り込むかを決めておくと、重複が減る。
- 約束事はAGENTS.mdに：チームで決めたルール（ページの書き方、資料の名前の付け方など）はAGENTS.mdに書く。人もエージェントも同じルールに従える。
- 使うエージェントがばらばらでもよい：AGENTS.mdを共通にしておけば、ある人はCopilot、別の人はほかのエージェント、という使い方もできる。

## 気をつけること

- 非公開を基本に：資料には、他人が書いた記事や、公開してはいけない情報が含まれることがある。他人の文章をまるごと公開のリポジトリに置くと、著作権の問題になりうる。公開するかどうかは、内容を確かめてから決める（[AIを使うときの倫理とルール](ai-ethics.md)）。
- 個人情報を置かない：インタビューやアンケートの記録を資料にする場合は、名前などを伏せる。
- エージェントも間違える：要約の誤り、資料にないことの書き足し、リンクの間違いが起きることがある。重要な事実は元の資料で確かめる（[AIの答えを確かめる](checking-ai-output.md)）。
- 利用の上限に注意：エージェントの利用には、プランごとの上限があることが多い。大量の資料を一度に取り込むと、上限に早く達することがある（[GitHub Copilotとは](copilot-overview.md)）。
