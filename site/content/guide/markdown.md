## Markdownとは

Markdown（マークダウン）は、ふつうの文字だけで、見出しや箇条書きなどの書式を表す書き方です。たとえば、行の頭に`#`を付けると見出しに、`-`を付けると箇条書きになります。ファイル名の最後は`.md`にします。

Markdownのファイルは、メモ帳のような単純なアプリでも読み書きでき、GitHubやVS Codeで開くと、書式の整った見た目で表示されます。この授業では、READMEも、知識ベース（Wiki）のページも、このサイトの元の文章も、すべてMarkdownで書かれています（[LLM Wiki](../../../wiki/concepts/llm-wiki.md)）。

AIとの相性がよいことも、Markdownの大きな利点です。AIは文章の構造をMarkdownで表すことに慣れていて、チャットの答えもMarkdownで返すことがよくあります。AIエージェントに知識ベースを書いてもらうときも、Markdownなら、人もAIも同じファイルをそのまま読み書きできます。

## 見出し

行の頭に`#`と半角スペースを書くと見出しになります。`#`の数が多いほど小さな見出しになります。

```
# ページの題名（一番大きな見出し）
## 大きな節
### 小さな節
```

`#`の後の半角スペースを忘れると、見出しになりません。一つのファイルでは、`#`の見出しは最初の一つだけにして、その下を`##`と`###`で分けるのが一般的です。この授業のWikiも、そのように書いています。

## 段落と改行

段落と段落の間には、空の行を一つ入れます。空の行がないと、続けて一つの段落として表示されます。

ここで、日本語ならではの注意があります。段落の途中で改行すると、表示のときに改行が半角スペースに置き換わり、日本語の文の途中に不自然な空白が入ってしまいます。英語は単語の間に空白を入れる言葉なので、これで困らないのですが、日本語では困ります。

<div class="compare" markdown="1">
<div class="bad" markdown="1">

書き方（段落の途中で改行）

```
GitHubで
知識ベースを作ります。
```

表示：GitHubで␣知識ベースを作ります。（␣のところに空白が入る）

</div>
<div class="good" markdown="1">

書き方（一つの段落を一行で）

```
GitHubで知識ベースを作ります。

次の段落は空の行のあとに。
```

表示：二つの段落が、空白なしで正しく表示される。

</div>
</div>

そこで、日本語のMarkdownでは「一つの段落は一行で書く」と決めておくのが安全です。エディターの画面では長い行が折り返して表示されるので、書くときに困ることはありません。

## 箇条書き

行の頭に`-`と半角スペースを書くと、点の付いた箇条書きになります。`1.`のように数字とピリオドを書くと、番号つきの箇条書きになります。箇条書きの中に箇条書きを入れるときは、行の頭に半角スペースを4つ入れて字下げします。

<div class="compare" markdown="1">
<div markdown="1">

書き方

```
- アンケートを作る
- 結果をまとめる
    - 表にする
    - グラフにする

1. 質問を考える
2. 先生に見てもらう
```

</div>
<div markdown="1">

表示

- アンケートを作る
- 結果をまとめる
    - 表にする
    - グラフにする

1. 質問を考える
2. 先生に見てもらう

</div>
</div>

箇条書きの各項目も、一行で書きます。項目の名前と説明を分けたいときは、太字を使わずに全角のコロン（：）で区切ります（例：「目的：学内のWi-Fiの使いやすさを調べる」）。

GitHubでは、`- [ ] 質問を考える`のように書くと、チェックボックスの付いた「やることリスト」になります。IssueやREADMEで、作業の進み具合を示すのに便利です（[ブランチとプルリクエストでの共同作業](github-collaboration.md)）。

## リンクと画像

リンクは、`[表示する文字](行き先)`の形で書きます。行き先には、ウェブのURLのほか、同じリポジトリの中のファイルを相対パス（いまのファイルから見た位置）で書けます。

<div class="compare" markdown="1">
<div markdown="1">

書き方

```
[GitHub](https://github.com)を開く。

日程は[こちら](schedule.md)。
```

</div>
<div markdown="1">

表示

[GitHub](https://github.com)を開く。

日程は<a href="#リンクと画像">こちら</a>。

</div>
</div>

画像は、リンクの前に`!`を付けて`![画像の説明](images/photo.png)`のように書きます。`[]`の中の説明は、画像が表示できないときや、目の見えない人が読み上げ機能を使うときに使われるので、何の画像かが分かる言葉を書きます。画像のファイルは、リポジトリの中に`images`などのフォルダーを作って置くと整理しやすくなります。

ファイル名とフォルダー名は、半角の英小文字・数字・ハイフンにします（例：`images/wifi-map-2026.png`）。日本語のファイル名は、OS（WindowsやmacOS）によって文字の扱いが違うため、GitHubとの間で問題を起こしやすく、リンクのURLも読みにくくなります。ページの日本語の名前は、ファイルの中の`#`の見出しに書けば十分です。

## 表

`|`（縦棒）で列を区切り、2行目に`:----`のような区切りの行を書くと、表になります。

<div class="compare" markdown="1">
<div markdown="1">

書き方

```
| 日付 | 内容 |
| :---- | :---- |
| 10月7日 | GitHubのデモ |
| 10月14日 | プロジェクトの相談 |
```

</div>
<div markdown="1">

表示

| 日付 | 内容 |
| :---- | :---- |
| 10月7日 | GitHubのデモ |
| 10月14日 | プロジェクトの相談 |

</div>
</div>

表のセルの中では改行できません。長い説明は表の外に書きましょう。表を手で揃えるのは面倒なので、「この内容をMarkdownの表にして」とAIに頼むのも手です。

## コードと記号

文の中で、ファイル名、コマンド、記号などを示すときは、`` ` ``（バッククォート）で囲みます。囲んだ部分は等幅の文字で表示され、中の記号は書式として扱われません。

<div class="compare" markdown="1">
<div markdown="1">

書き方

```
`README.md`を開き、`#`の数を確かめる。
```

</div>
<div markdown="1">

表示

`README.md`を開き、`#`の数を確かめる。

</div>
</div>

何行にもわたるコードや、書式を付けずにそのまま見せたい文章は、`` ``` ``（バッククォート三つ）だけの行で上下を囲みます。

````
```
ここに書いた文字は、
そのままの形で表示される。
```
````

本文の中で`*`、`_`、`~`、`#`など、Markdownの記号として使われる文字をそのまま見せたいときも、バッククォートで囲んでおくと安全です。

## 太字を使わない理由

Markdownには、アスタリスク二つ（`**`）で囲むと太字になる書き方があります。ところが、日本語の文で使うと、太字にならずに記号がそのまま表示されてしまうことがよくあります。

<figure class="fig">
{{svg:markdown-bold-rule.svg}}
<figcaption>同じ「重要」でも、かぎ括弧を記号の内側に入れると、GitHubでは太字として認識されず、アスタリスクがそのまま表示される。</figcaption>
</figure>

GitHubのMarkdownは、CommonMarkという共通の規則にもとづいています。この規則では、強調の記号が「始まり」や「終わり」として認められるかどうかが、記号の前後の文字で決まります。記号の内側にかぎ括弧や句読点があり、外側に（空白ではない）ふつうの文字があると、その記号は強調の始まりや終わりとは見なされません。英語では単語の間に空白があるので問題になりにくいのですが、空白を入れない日本語では、この条件にすぐ当てはまってしまいます。

| 書き方 | GitHubでの表示 |
| :---- | :---- |
| `これは**「重要」**です。` | 太字にならず、記号がそのまま出る。 |
| `**重要。**次に進む。` | これも太字にならない（終わりの記号の内側が句点）。 |
| `これは**重要**です。` | 太字になる。 |

どの書き方なら大丈夫かを覚えて使い分けるのは大変ですし、AIが書いた文章では、うまくいかない形がよく混ざります。そこで、この授業の知識ベースでは、太字や斜体をそもそも使わないことにしています。強調したいときは、次の方法を使います。

- 見出しにする：大事な内容は、それだけで節にする。
- 箇条書きにする：要点を短い項目に分けて並べる。
- かぎ括弧で囲む：「必ず非公開にする」のように、言葉を目立たせる。

## 日本語で書くための規則のまとめ

この授業の知識ベースの約束事（[AGENTS.md](../../../AGENTS.md)の「日本語で書くための規則」）から、Markdownの書き方に関わるものをまとめました。自分のプロジェクトでも、そのまま使えます。

| 規則 | 理由 |
| :---- | :---- |
| 一つの段落は一行で書く | 段落の途中の改行は、表示のときに空白になる。 |
| 太字・斜体を使わない | かぎ括弧や句読点と隣り合うと、記号がそのまま表示される。 |
| 項目名と説明は全角のコロンで分ける | 太字を使わずに、見出しと説明を区別できる。 |
| 記号はバッククォートで囲む | `*`や`#`が書式として解釈されるのを防ぐ。 |
| 句読点と括弧は全角を使う | 日本語の文として自然に見える。範囲は「〜」で示す。 |
| 日本語と英数字の間に空白を入れない | 「GitHubのリポジトリ」のように書くと、表示が揃う。 |
| リンクは`[表示名](相対パス)`で書く | GitHubの画面でも、そのままリンクとして働く。 |
| ファイル名は半角の英小文字・数字・ハイフン | OSによる文字の違いで問題が起きるのを防ぐ。 |

AIエージェントに文章を書いてもらうときは、この規則を指示ファイル（`AGENTS.md`など）に書いておくと、毎回伝えなくても守ってくれるようになります（[自分のプロジェクトに知識ベースを作る](knowledge-base.md)）。それでも、書き上がったものに`**`や段落の途中の改行が混ざっていないか、ときどき確かめましょう。

## README.mdを書く

README.md（リードミー）は、リポジトリの一番上の階層に置く説明のファイルです。GitHubでリポジトリを開くと、ファイル一覧の下に自動で表示されます。初めてそのリポジトリを見た人（未来の自分やAIエージェントも含む）が、最初に読む文書です。

プロジェクトのREADMEには、たとえば次のようなことを書きます。

```
# 学内Wi-Fi調査プロジェクト

「AIとの探検ゼミナール」の第3班のプロジェクトです。世田谷キャンパスの教室Wi-Fiの使いやすさを、アンケートと計測で調べます。

## ファイルの構成

- `survey/`：アンケートの質問と結果
- `notes/`：打ち合わせのメモ
- `wiki/`：調べたことをまとめた知識ベース

## 進め方

作業はブランチで行い、プルリクエストで確認してからmainに取り込みます。
```

メンバーの名前などの個人情報を書くかどうかは、リポジトリを公開するかどうかと合わせて、チームで決めてください。

## プレビューで確かめる

書いたMarkdownがどう表示されるかは、書きながら確かめられます。

- GitHubの画面：ファイルの編集の画面で、<span class="ui">Edit</span>の横の<span class="ui">Preview</span>のタブを押す。
- VS Code：Markdownのファイルを開いた状態で、Ctrl＋Shift＋V（MacはCommand＋Shift＋V）を押すとプレビューが開く。Ctrl＋K（MacはCommand＋K）を押してからVを押すと、編集の画面の横にプレビューが並ぶ（[VS CodeでCopilotを使う準備](vscode-copilot-setup.md)）。

Markdownの細かい書き方は、表示するツールによって少しずつ違います。このサイトのように、GitHub以外の方法でMarkdownを表示する場合もあるので、迷ったときは、このページで紹介した基本の書き方だけを使うのが安全です。GitHubでの書き方の詳細は、公式の案内（[GitHub Docs：基本的な書き方とフォーマットの構文](https://docs.github.com/ja/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)）にまとまっています。
