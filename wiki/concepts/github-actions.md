# GitHub Actions

リポジトリで起きた出来事をきっかけに、テストやサイトの公開などの作業を自動で行うGitHubの仕組み、GitHub Actionsについてのページ。

## 概要

GitHub Actionsは、作業を自動化するためのGitHubの仕組みです。たとえば、プルリクエストが作られるたびに自動で確認を走らせたり、変更が取り込まれたらサイトを公開し直したりできます。新しいIssueに自動でラベルを付けるような、開発以外の用途にも使えます。設定はリポジトリの中のファイルに書くので、作業の手順も履歴として残ります（[資料：GitHub Actionsの基本](../sources/web-github-actions-overview.md)、2026年11月1日に確認）。

## 五つの部品

- ワークフロー：自動化された一連の処理の全体。`.github/workflows`フォルダーに置くYAMLファイルで定義する。
- イベント：ワークフローを動かすきっかけ。プルリクエストの作成、Issueの作成、プッシュなど。手動や決めた時刻でも動かせる。
- ジョブ：同じ場所で実行される手順のまとまり。既定では並行して動き、依存を指定すると順番に動く。
- アクション：繰り返し使える部品。リポジトリの取得や環境の準備などを、自分で書かずに呼び出せる。
- ランナー：実際に処理を実行するサーバー。GitHubが用意するLinux、Windows、macOSの仮想マシンを使え、実行のたびに新しい環境で動く。

## このリポジトリでの使われ方

この知識ベースのリポジトリでも、`.github/workflows/`のワークフロー「サイトの公開」が使われています（資料外の補足：リポジトリの内容にもとづく）。プルリクエストが作られると、サイトを組み立ててリンク切れがないかを確かめ、`main`に取り込まれると、GitHub Pagesに公開します。プルリクエストの画面に出る確認（チェック）の正体は、このようなワークフローです。確認が失敗したときは、原因を直してから取り込みます（[GitHub Pages](github-pages.md)、[GitHubフロー](github-flow.md)）。

## 初心者が覚えておくこと

- ワークフローの書き方を覚える必要はありません。必要になったら、AIエージェントに日本語で頼めば書いてもらえます（資料外の補足）。
- 確認が赤（失敗）になったら、画面の詳細からログを開き、そのログをエージェントに見せて原因を聞くのが早道です（資料外の補足）。
- 自動で動く処理は、リポジトリの設定やプランによって使える量に上限がある場合があります。授業の組織での扱いは未確認です。
